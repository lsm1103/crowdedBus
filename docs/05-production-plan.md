# 开发计划与验收

## 1. 推荐路线

对新人团队，最短路径不是先实现 8 个角色或商业化，而是先在一台手机上验证“推挤和急刹是否有趣”，再接入联网。下面的阶段按风险由高到低排序，任一阶段未通过都应优先修正，而不是继续堆内容。

## 2. 里程碑

| 阶段 | 目标 | 交付物 | 通过条件 |
| --- | --- | --- | --- |
| M0：立项 | 明确体验与范围 | 本文档、风险清单 | 团队能用一句话讲清玩法 |
| M1：单机灰盒 | 验证动作与空间 | 方块角色、车厢、移动/推挤/扶手/急刹 | 4 人轮流试玩仍愿意重开 |
| M2：单机完整局 | 验证 3 分钟节奏 | 阶段、事件、淘汰、结算、AI | 每局都有清楚的胜负原因 |
| M3：联机原型 | 验证 2～8 人同步 | 房间、同步、重连、机器人补位 | 8 人压力测试无阻断不同步 |
| M4：可玩测试版 | 验证新手与可分享性 | UI、引导、占位美术、微信邀请 | 新用户可独立完成一局 |
| M5：发布候选 | 品质与合规 | 正式素材、埋点、兼容性、审核材料 | 关键缺陷清零并满足平台要求 |

## 3. 首周任务建议

1. 用灰盒搭出一个固定大小的车厢，标出车门、座位和 4 个扶手。
2. 实现单个角色的移动、冲刺、推挤和抓扶手；角色技能在这些规则稳定后按“学生冲刺 → 小李锚定 → 其他技能”的顺序接入。
3. 加入一个急刹事件与边界淘汰。
4. 找 3～5 位非开发者试玩，记录他们在哪一步困惑、在哪一刻笑出来。
5. 根据观察修改碰撞、击退和提示，再决定是否开始网络原型。

## 4. 测试清单

### 功能测试

- 房主开始、玩家加入/退出、机器人补位、重连、结算和再来一局均能闭环。
- 任何事件都不会让角色卡进墙体、永久失控或无提示淘汰。
- 客户端与服务端对胜负、剩余人数、倒计时的显示一致。

### 可玩性测试

- 新玩家不看说明能在第一次急刹时找到扶手或理解自己为何失败。
- 推挤有策略价值，但不出现持续围殴无法操作的体验。
- 领先者不会仅靠占据唯一安全位置就能无风险获胜。

### 设备与网络测试

- 覆盖至少一台低/中/高性能目标设备。
- 分别测试正常网络、高延迟、短暂断网和重连。
- 连续进行多局，检查内存、发热、资源重复加载和连接泄漏。

## 5. 风险登记册

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 联机不同步 | 玩家看到的位置与淘汰原因不一致 | 权威服务端、保留对局日志、先小房间测试 |
| 推挤不公平 | 被连续控制或误判命中 | 受击保护、清晰碰撞体、录像复盘 |
| 信息拥挤 | 玩家看不清角色与危险区 | 限制同屏特效、强化危险色与轮廓 |
| 内容膨胀 | 角色/皮肤先于基础规则完成 | 以 M1/M2 验收作为内容立项门槛 |
| 微信审核或能力差异 | 后期才发现接口/性能限制 | 早期接入真机与平台能力验证 |

## 6. 已确认决策

以下内容已作为当前设计基线：

1. 画面采用斜 45° 2.5D。
2. 推挤先验证物理碰撞方案；达到技术设计中的降级门槛时切换到规则化距离判定。
3. 角色主动技能首发。
4. 好友房与微信邀请首发。

仍待确认：三种美术方向选哪一种、目标低端机型基线、服务端部署地区与预算。引擎先按 Cocos Creator 3.8 LTS 做两周验证，通过后再正式锁定。
