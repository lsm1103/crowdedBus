# 技术设计

## 1. 已确定的技术前提

- 发布平台：微信小游戏，横屏。
- 画面：斜 45° 2.5D，正交相机，角色在车厢 XZ 平面移动。
- 对局：2～8 名真人，好友房首发，约 3 分钟一局。
- 操作：移动、冲刺、普通推挤、扶手交互和角色主动技能。
- 碰撞：先验证物理碰撞方案；如果无法满足一致性、性能和公平性，再降级为规则化距离判定。
- 服务端：Go，权威裁定对局。

## 2. 结论：推荐技术栈

| 层级 | 推荐选择 | 原因 |
| --- | --- | --- |
| 客户端引擎 | Cocos Creator 3.8 LTS | 官方支持微信小游戏构建、TypeScript、2D/3D 混合与 3D 物理 |
| 客户端语言 | TypeScript，开启严格类型检查 | 新人更容易发现空值、协议和状态错误 |
| 场景表现 | 低模 3D 场景/角色＋正交相机＋2D UI | 直接实现斜 45° 2.5D、遮挡和角色换装 |
| 客户端物理原型 | Cocos 3D 物理，优先验证 Bullet/`ammo.js` 构建 | 微信小游戏构建链提供对应 Wasm 选项，但必须真机验证包体和性能 |
| 实时通信 | 安全 WebSocket＋二进制 Protobuf | 微信端能力直接、支持双向低延迟；协议可由 Go/TS 生成 |
| 服务端语言 | Go 1.26.x | 当前受支持版本，适合高并发连接和简单部署 |
| WebSocket 库 | `coder/websocket` | API 简洁、支持上下文、依赖少；在压力测试不达标时再换事件驱动库 |
| 业务接口 | Go 标准库 `net/http` | MVP 不需要大型 Web 框架 |
| 持久化 | PostgreSQL | 保存账号映射、角色解锁和结算记录 |
| 临时状态 | Redis | 房间邀请码、在线状态、匹配队列和短期锁 |
| 可观测性 | 结构化日志＋Prometheus 指标＋错误上报 | 能复现延迟、掉线和不同步问题 |

截至 2026 年 7 月，Cocos Creator 3.8 是官方 LTS 文档线，并提供微信小游戏构建、分包和 Bullet/`ammo.js` 的 Wasm 构建选项。Go 官方当前稳定线为 1.26；实际项目锁定最新的 1.26.x 修订版，不锁死补丁版本。

## 3. 客户端实现方案

### 3.1 场景与相机

- 车厢使用真实 3D 几何体，但玩法逻辑只存在于 XZ 平面，不允许自由跳跃。
- 正交相机固定俯角约 45°，水平偏角在灰盒阶段测试 30°、45°、60°三档。
- 近侧车壁和车顶在遮挡玩家时淡出；角色头顶显示短昵称、技能预警和危险状态。
- 角色使用胶囊或圆柱碰撞体；座位、车门和行李使用盒碰撞体。
- UI 使用独立 Canvas：左下摇杆，右下普通推挤、技能和交互按钮。

### 3.2 渲染约束

- 采用无光照或轻量卡通材质，灯光尽量烘焙；低档机关闭实时阴影。
- 同屏角色上限按 8 真人＋8 AI 设计，特效使用对象池。
- 角色骨骼、材质数量和贴图尺寸在美术定稿后建立硬预算；首轮技术验证先用统一模型。
- 大厅、车厢和角色资源拆成 Asset Bundle；首包只保留启动、登录和最低可玩资源。

### 3.3 客户端代码分层

```text
assets/scripts/
  app/              启动、场景流转、生命周期
  platform/wechat/  微信登录、分享、前后台、网络状态
  lobby/            好友房、匹配、大厅 UI
  game/domain/      纯规则类型、输入命令、技能配置
  game/view/        角色、场景、动画、音效和特效
  game/prediction/  本地预测、快照缓存、误差校正
  network/          WebSocket、协议、心跳、重连
  ui/               通用界面和 HUD
  config/           数值表、版本与校验
```

`domain` 不直接引用 Cocos 节点，便于编写自动测试；`view` 只表现服务端结果，不决定伤害、击退或淘汰。

## 4. Go 服务端方案

### 4.1 先做模块化单体

首发不需要微服务。一个 Go 仓库生成三个可执行程序即可：

```text
cmd/gateway      HTTPS、登录、WebSocket 接入、限流
cmd/game         房间 actor、固定 tick 模拟、快照广播
cmd/worker       结算落库、清理过期房间、异步统计

internal/auth        微信登录态换取与会话
internal/room        好友房、房主、准备、邀请令牌
internal/match       对局状态机
internal/simulation  移动、碰撞、技能和车辆事件
internal/protocol    Protobuf 生成代码与版本兼容
internal/storage     PostgreSQL、Redis 访问
internal/telemetry   日志、指标、追踪标识
```

原型阶段可把三个入口合并成一个进程部署；代码边界保留，出现真实扩容需求后再拆进程。不要在首版引入 Kubernetes、Kafka 或完整微服务治理。

### 4.2 房间并发模型

- 每个对局房间由一个 goroutine 顺序处理，房间内部不共享可变状态。
- 网络读协程只解析和校验输入，再投递到房间输入队列。
- 房间 goroutine 以固定 20 Hz tick 更新；耗时超过 50 毫秒必须记录告警。
- 每 2 个 tick 广播一次快照，即目标 10 Hz；关键技能、淘汰和事件额外可靠发送。
- 房间结束后生成不可变结算结果，再异步落库。

这种 actor 式设计比给每个玩家状态加锁更容易推理，也更适合新人排查竞态。

### 4.3 数据归属

| 数据 | 存放位置 | 原因 |
| --- | --- | --- |
| 对局实时位置、技能冷却 | 游戏进程内存 | 高频变化，不落数据库 |
| 房间邀请码、所在节点、过期时间 | Redis | 跨进程查找和自动过期 |
| 玩家账号、解锁、软币 | PostgreSQL | 需要事务和长期保存 |
| 对局摘要、异常快照 | PostgreSQL/对象存储 | 复盘和客服排障 |

MVP 不做游戏进程崩溃后的无感迁移。崩溃时该局判为无效并退还消耗；先保证可观测和快速重开，比复制每一帧状态更划算。

## 5. 物理碰撞与权威同步

### 5.1 为什么不能直接相信客户端物理

Cocos 客户端和 Go 服务端不是同一个物理运行时。即使输入相同，浮点误差、帧率和碰撞求解顺序也会让结果逐渐分叉。因此客户端物理可用于即时反馈和表现，最终位置、推挤命中、掉出车门和胜负必须由 Go 服务端决定。

### 5.2 推荐的“物理优先”实现

服务端实现一套只针对车厢平面的轻量物理解算器，而不是移植完整 3D 引擎：

- 世界坐标使用毫米整数或定点数，避免跨平台浮点漂移。
- 玩家为圆形/胶囊投影，墙和座位为轴对齐或有限方向的盒体。
- 移动使用运动学速度；推挤和车辆事件施加冲量与短时速度。
- 使用空间哈希查找附近碰撞对，按稳定 ID 顺序迭代解穿透。
- 每 tick 固定进行 2～4 次顺序冲量求解；限制最大速度和最大位移。
- 扶手不是物理关节，而是带范围条件的约束状态，按比例抵消冲量。

它仍然是物理碰撞：角色会接触、挤压、传递冲量并产生连锁位移；只是去掉了旋转、跳跃和复杂关节，使服务端可复现、可测试。

### 5.3 客户端预测

1. 客户端立即应用自己的移动输入并发送 `InputCommand(sequence, clientTick, direction, buttons)`。
2. 服务端验证速度、冷却和状态，在权威 tick 中模拟。
3. 服务端返回快照和最后确认的输入序号。
4. 客户端从权威位置重放未确认输入；小误差在 100～150 毫秒内平滑，大误差直接纠正并记录。
5. 其他玩家保持约 100 毫秒快照缓冲并插值，避免抖动。

推挤与技能先在客户端播放前摇，不立即播放“命中”结论；收到服务端事件后再播放击中特效。这样稍慢一点，但结果可信。

### 5.4 明确的降级门槛

在两周网络物理验证中，满足任一条件就停止扩大自研物理解算器，改用“运动学移动＋距离/扇形命中＋预设击退曲线”：

- 8 人、120 毫秒往返延迟下，超过 5% 的强碰撞需要大幅位置纠正。
- 服务端单房间 20 Hz 模拟的 P99 耗时超过 10 毫秒。
- 低端目标机因客户端物理无法稳定达到 30 FPS。
- 两周后仍存在高频穿墙、叠人或不同步且无法写出稳定复现测试。

降级只替换碰撞判定层，角色、美术、输入、协议和房间系统无需推倒重写。

## 6. 网络协议

### 6.1 连接

- 使用 `wss://`，域名提前加入微信平台合法域名配置。
- 登录通过 HTTPS 获取短期游戏会话；WebSocket 握手携带一次性票据，不直接传微信敏感凭据。
- 心跳建议 10 秒一次；连续 3 次无响应进入断线状态。
- 断线 15 秒内允许凭重连令牌回到原房间并获取完整快照。

### 6.2 消息类别

```text
客户端 → 服务端：登录、创建/加入房间、准备、开始、输入命令、表情、重连
服务端 → 客户端：房间快照、对局快照、技能事件、环境事件、淘汰、结算、错误
```

所有消息带协议版本、消息类型、序号和服务端 tick。高频快照采用二进制 Protobuf；大厅低频接口仍可用 JSON。首版不做自定义加密，使用 TLS，并对输入频率、消息大小和状态合法性做严格限制。

## 7. 好友房首发方案

```text
房主创建房间 → 服务端生成短期邀请令牌 → wx.shareAppMessage 分享
→ 好友从分享入口启动 → 微信登录 → 兑换令牌 → 加入房间所在游戏节点
→ 准备/房主开始 → 锁定角色与配置版本 → 对局
```

- 邀请令牌只保存随机 ID 和签名，不在分享路径中暴露真实房间状态。
- 令牌默认 30 分钟过期；房间开始后，新加入者进入观战或收到“本局已开始”。
- 同一玩家重复点击邀请应幂等加入，不能生成多个角色。
- 房主掉线时按进入顺序转移房主；对局中房主无额外裁定权。
- 2～7 人时由房主选择直接开始或加入低攻击性 AI，不强制等待满员。

## 8. 测试与性能预算

### 必做自动测试

- 相同随机种子和输入日志重复执行，最终状态完全一致。
- 角色互推、三人夹击、墙角、门边、扶手和所有技能的边界测试。
- 协议向前兼容、重复消息、乱序输入、超频输入和非法数值测试。
- 房主掉线、成员掉线、重连、房间过期和结算幂等测试。

### 真机验收

- 低/中/高三档真机，8 玩家＋目标 AI 数量，连续玩 10 局。
- 客户端目标 30 FPS 下不持续掉帧；内存和发热以平台性能工具实测建线。
- 网络分别模拟 60/120/200 毫秒往返延迟和 1%/5% 丢包。
- 记录服务器 tick 耗时、输入到达延迟、快照大小、纠正距离和重连成功率。

## 9. 两周技术验证交付物

第一周完成斜 45° 灰盒车厢、两个真人或机器人、移动、普通推挤、墙体和急刹；第二周把同一输入送入 Go 权威服务端，扩展到 8 人并加入网络延迟。最终必须产出一份数据报告，而不是凭手感选择物理方案。

通过条件：120 毫秒往返延迟下，普通移动无明显抖动；推挤结果能被双方理解；8 人服务端模拟留有足够余量；低端目标机稳定运行。未通过则按 5.4 节降级。
